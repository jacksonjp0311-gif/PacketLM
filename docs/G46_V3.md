# G46 / G46-U / G47 re-measurement on engine v3 (pre-registered before the runs)

## Engine changes (exact developer improvements; none changes a decision)

- Qualification scan:
  - breadth-first over distinct base sequences;
  - stops at 64 blockers, after which counts are lower bounds and `truncated` is set;
  - restricted by a relevance index (only primitives whose first relation leaves the frontier).
- Predictions and differences are computed only where a program can be defined.
- `geom.compose` and `geom.bits` iterate set bits only.

Checks: suite 151/151, `audit.scan_matches_bruteforce`, `audit.compose_matches_naive`,
24/24 mutations killed, and G45 decisions identical.

Also present but off: operators (`--operators` is not passed in any of these runs).

## Purpose

The v2 runs found the utility problem: `A_36(C‖B)` = −7.0 and `A_24(C‖B)` = −23.1. This
re-measurement asks how much of it was implementation cost rather than retained-knowledge cost.

## Protocol

Same harnesses, seeds, arms, budgets and thresholds as docs/G46.md (with amendment 1),
docs/G46U.md and docs/G47.md. Nothing is re-tuned.

- The v2 results stay as the registered G46 result: 26/27, not passed.
- The v3 results are reported beside them and do not replace them.
- Prediction: decisions differ from v2 only through investigation order, because the blocker
  list order changed. Thresholds should be about the same.
- `A(C‖B)` will still be negative, since C still carries all retained knowledge into every call.
- Open question, answered as it falls: whether `A(C‖B)` crosses 0 anywhere on the
  compositional curriculum.

## Results (engine v3, `engine_sha256` 2df9fd27…; evidence in docs/evidence/v3/)

Decisions match the prediction.

- **Same in every engine arm (C, B, P, F, S, G, N) and every seed:** acquisitions, sealed
  correctness, metrics and threshold outcomes. C acquires 36/36/35, B 32/32/31, and 0 are
  wrong-qualified.
- **Changed:** the number of examples plus questions, because the blocker order changed. For example,
  C has 112 / 119 / 109 in v3 against 112 / 127 / 116 in v2.
- **Also changed:** the in-process reference arm R. It receives the teacher answers C received,
  so its results moved with C's questions: 31/154, 33/156, 31/153 in v3 against 30/152, 33/155,
  33/158 in v2.
- **G47 and G46-U:** acquisitions, correctness and question counts are identical.
- **Result:** seed 33 threshold 6 still fails, at the same task, so **G46 stays NOT passed
  (26/27)**.

### G47 (library vs primitives at depth 2 and depth 3)

- **H3 is true** in all seeds, as in v2: K acquires 36/36/35 tasks and Q 15.
- **H5 flips from false (v2) to true.** At depth 3, L's CPU per acquired task is below M's in
  every seed: 0.68 / 0.70 / 0.74 s against 0.85 / 0.89 / 0.88 s. These are replicate figures;
  the first v3 run gives the same ordering.
- **Timing artifact in the first G47 v3 run.** Five of the twelve arm-runs each had one late
  task or family charged about 34 s (11:Q t36, 11:L t31, 11:M t33, 22:K t33, 22:Q family-6
  maintenance). The other tasks cost about 1.5 s or less.
  - The size was the same each time, the five fell at about the same point in the run, and
    wall time ≈ CPU time. That points to a single host stall, not engine work.
  - Replaying 22:K deterministically gave identical evaluation and execution counts for that
    task (967 / 1621) at 2.7 s, with a profiler attached.
  - I therefore ran **one declared replicate**: same commit and harness, isolated, nothing else
    running (docs/evidence/v3/g47_replicate/). It had no outliers.
  - Both runs are kept. The first run is not deleted or replaced.

| contrast | v2 | v3 first run (stall) | v3 replicate |
|---|---|---|---|
| `A_36(K‖Q)` | −0.76 | −0.23 [−2.71, +0.57] | **−0.41 [−0.47, −0.34]** |
| `A_36(L‖M)` | −0.82 | −0.16 [−0.26, −0.09] | **−0.25 [−0.27, −0.23]** |
| `A_36(K+maint‖Q+maint)` | −0.50 | +0.11 [−0.29, +0.48] | −0.27 [−0.30, −0.23] |

Q and M are heavily censored (61 and 36 tasks), so these A values are lower bounds for the
library arm. They compare total task cost: the library arm also solves 21 or 12 more tasks.

### Reading

- About two thirds of v2's negative `A(C‖B)` was implementation cost, not retained knowledge.
- What remains is the utility problem, and it is real: C still carries 2.5 MB of state into
  every call. Phase B has the same process count in C and B (127), but costs 0.181 s per process
  in C against 0.055 s in B.
- Profiling one C call: load ≈ 0.07 s (JSON plus per-fact `bind` re-check) and save ≈ 0.14 s.
  The save time is two more full validations plus the write. All of it scales with state size.
- The reuse saving against primitives (`A^reuse` > 0) survives, but is smaller (+0.115), because
  P got cheaper too.
- Next steps, in order:
  1. Exact persistence work (v4, below). This does not change any decision.
  2. The pre-registered adaptive-retention experiment (docs/ARET.md), which targets the size
     scaling itself.
