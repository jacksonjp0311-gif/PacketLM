# G56: the long-lived engine protocol, charged equally to every arm

Decision at 03:59 (America/New_York, 2026-11-27), delegated by James: the per-call protocol change
is approved, under this control rule:
- every arm, including B (empty state), P and F, gets the identical long-lived engine and loading
  protocol, so no arm is advantaged by how it is charged;
- B still starts every task from an empty state: a fresh in-memory state, never a reused one;
- the new protocol's contrasts are reported, with the old per-process accounting as a secondary,
  descriptive line;
- evidence-gated maintenance re-asks are allowed only if they keep their soundness guarantees and
  are pre-registered. **They are not part of G56**: the teacher's re-asks are unchanged.

Pre-registered before any registered seed is run; new seeds, at least 7 per curriculum,
instrument 70297af. Replies must be identical to the per-process engine, which is a run guard.

## 1. Why (G54)

G54 showed that `--lean` cut 17% (comp) and 34% (unrel) of the library learner's cost exactly,
but the protocol of one process per call sets a floor (f0 = 25.9 ms per process). On unrelated
knowledge, C's 911 processes × f0 already exceeded B's whole 11.4 s. The remaining per-call work
is also proportional to the state: a full load (parse, checksum, validation) and a full save
(serialization, validation, backup, atomic write) in every call.

## 2. Mechanism: `python -m packetlm.serve` (packetlm/serve.py)

One process serves many calls. A call has the same meaning as one `python -m packetlm.engine
STATE [flags] line ...` process: its lines are turned by a fresh `Engine` object over the state,
and the call is made durable before its reply is returned. Only two things change: where the state
lives between calls, and how it is made durable.

- **State in memory.** The state of the open path stays in memory. A call on another path (or
  with other flags) first closes the open one with a snapshot, then opens the new one from disk
  exactly as the per-process engine does (`Engine.open`), followed by journal recovery. A path
  with no file starts from `empty_state()`, so B tasks (a new path per task) start empty.
- **Per call:** a fresh `Engine` over the state (no per-object cache survives a call), the lines,
  then `Engine.finish` (growth re-scans and archiving, the work `save` did first).
- **Validation.** The resulting state is checked in memory by the validator the per-process engine
  runs before every save (`validate_lean`, every structural check). Only the checksum is not
  computed, because no bytes are written.
- **Durability by journal.** `STATE.journal` holds a header naming the snapshot it extends, then
  one fsync'd record per call (flags, lines, sha256 of the replies).
- **Snapshots.** Every 64 calls, and on close, the state is written by the ordinary lean `save`:
  validated, previous primary kept as the backup, atomic replace, fsync. The journal then restarts
  on the new snapshot.
- **Recovery.** Load the snapshot as the per-process engine does, then replay the journal call by
  call through fresh `Engine` objects.
  - Every replayed call must reproduce its recorded reply hash, or the load fails with StateError:
    no silent reconstruction.
  - A torn final record is ignored; its call never returned a reply.
  - A journal whose header names the backup's checksum (a crash between a snapshot and the journal
    restart) is already contained in the primary and is dropped. Any other mismatch is an error.
  - **Correction (verify-d6cbcf3 S1).** As registered (d6cbcf3) this held only when a previous
    snapshot existed: a crash inside a new path's *first* snapshot left a journal with base `null`
    beside the primary, and the path could not be reopened. No data was lost and no G56 run was
    affected (a crash ends a run). Fixed in G57's commit: a new path gets an empty snapshot at
    open, so every journal names a base; a journal whose base is the backup is replayed onto the
    backup and dropped only if the result is exactly the primary's state text, else refused; a
    journal beside no state file (deleted state, verify-d6cbcf3 Low 1) is refused, never replayed
    onto an empty state; the per-process engine refuses a path whose server journal holds records
    (Low 2) instead of reading the older snapshot. Reset a path by deleting STATE, STATE.bak and
    STATE.journal.
- **A failed call keeps nothing,** as when an engine process fails. The open state is dropped, and
  the next call reloads from snapshot and journal.
- **Process-level caches.** The only one is `field.bits_for` (`lru_cache` of a pure function).
  It is shared by every arm under this protocol, B included; it holds no state.
- **Not supported:** adaptive retention (it counts engine constructions as calls) and non-lean
  snapshots. Both are refused.

**Accounting.** Each call is charged `cpu_total_s` = the server's CPU since the end of the previous
charged request. The first call therefore carries interpreter start-up and imports, and the
closing snapshot is added to the run's last cost bucket. The per-call values thus sum to the
server's whole CPU. Harness inspections are excluded and reported separately: they read the open
state where the per-process harness read the file. A server's "processes" column counts calls.

**What does not change:**
- the engine's decisions, scan, qualification and replies;
- the teacher and its calls, including every maintenance re-ask;
- full validation of every state;
- backup and atomic snapshot guarantees;
- the flags (`--answers --bounded --lean`; B and P add `--no-library`).

## 3. Pre-registered measurement

- **Harness:** `benchmarks/g56.py`. The design is G54's: the G50 `complete` teacher, whole-process
  CPU with maintenance, the compositional (G46) and unrelated (G46-U) curricula.
- **Arms:** every role runs under both protocols on the same seeds.
  - Roles: C (persistent, library), B (empty state per task, no library), P (persistent, no
    library) and F (frozen after phase A; compositional only).
  - Protocols: per-process `Xl` (G54's accounting) and long-lived `Xs`.
- **Seeds (new):** comp **181–187**, unrel **191–197** (S = 7 each; amendment 1. The first registration's 161–167 / 171–177 are consumed). Instrument 70297af,
  unmodified, 5000 bootstrap resamples.
- **Command:** `python3 benchmarks/g56.py --out g56`.
- **Load.** The box is shared. The G55 registered run (L32 tail) and the verifier's own runs may
  be running at the same time. All 14 arms of a curriculum run interleaved in one pool, so load
  falls on both protocols. Contrasts against B are load-sensitive (verify-050bebd Info).
  `os.getloadavg()` is recorded in the receipt.

**Guards (run validity):**
- **E:** every `Xs` reply stream equals its `Xl` twin, call by call, on every seed of both
  curricula.
- 0 wrong-qualified sealed answers in Cl and Cs.
- The instrument is pinned and unmodified, every report ran, and the source is unchanged during
  the run.

**Decision rules (fixed now):** a claim needs the guards and a 95% CI wholly above 0.

| rule | contrast | claim if |
|---|---|---|
| **Ms** (protocol cut, both curricula) | A(Cs+maint ‖ Cl+maint) | CI > 0 |
| **L1s** (comp) / **L3s** (unrel): learning-to-learn under the long-lived protocol | A(Cs+maint ‖ Bs) | CI > 0 |
| **L2s** (library advantage) | A(Cs+maint ‖ Ps+maint) | CI > 0 |

**Secondary, descriptive (no claims):**
- the per-process contrasts A(Cl+maint ‖ Bl) and A(Cl+maint ‖ Pl+maint), on the same seeds;
- the protocol effect on the other arms: A(Bs ‖ Bl) and A(Ps+maint ‖ Pl+maint);
- Cs ‖ Bs and Cs ‖ Ps without maintenance;
- the F contrasts.

**Structure question (descriptive).** Under the long-lived protocol the process floor is paid once
per arm run, so what remains is per-call work. We report:
- C's maintenance share of its CPU;
- the change in A(C ‖ B) between protocols.

If A(Cs+maint ‖ Bs) is more negative than A(Cl+maint ‖ Bl), the per-process floor was hiding part
of the gap rather than causing it.

Tests at pre-registration: g44 139/139, suite 227/227 (11/11), G45 18/18, mutations 98/98 (0 crash kills).

**What this shows.**
- **The protocol is a large exact cut for every arm:** C −40% (comp) and −70% (unrel); B −52% and
  −93%; P −51% and −70%. Replies are identical to the per-process engine.
- **Charged equally, the gap to the empty-state learner widens.** comp goes 1.70× → 2.13×, unrel
  4.16× → 18.0×. B's per-process cost was almost entirely process overhead (unrel: 29 ms per call
  per-process, 2 ms long-lived).
- **The per-process floor was hiding part of the gap, not causing it.** The G54 question "is the
  remaining gap structural?" has a clear answer: it is not process structure.
  - **Unrelated:** 77% of C's cost is the teacher's maintenance re-asks. There are 504 calls, each
    asking every earlier item against a growing state, at 22 ms per call, against B's 2 ms per call.
    The rest is per-call work over the larger state (8.4 vs 2.0 ms).
  - **Compositional:** 90% is non-maintenance work at 49 ms per call (Bs: 26 ms): acquisition and
    scans over the library-extended space and a larger state.
- **The library still does not pay on compositional tasks** (L2s −0.53). On unrelated tasks C and P
  cost the same (L2s ≈ 0): the library is unused there (0 library tasks).
- **Next.** Cost proportional to the state:
  - evidence-gated re-asks (skip a re-ask whose dependency region is unchanged since its last
    answer; needs an exactness argument and its own pre-registration);
  - recall and scan costs that do not grow with unrelated state (indexing by relation and
    component).
