# G57b: state-independent per-call work for unrelated state (`--incremental`)

Registered before the run (2026-11-27). The registered run starts only with
`/workspace/REGISTERED_RUN.lock` in place (start time, experiment name), with no dev work beside it,
and the lock is removed right after. Every arm run is written to disk when it finishes.

## 1. Why (G57)

G57's rule F failed: with the relevant state fixed, per-task CPU of the G57 engine (`--indexed`) grew
from 2.26 ms at N = 0 to 206.6 ms at N = 16,000 unrelated facts, R_16000 = 91.9 [86.5, 95.7].
Profile of the G57 engine on the part S workload (dev seed 991; `docs/evidence/g57b/profile_before.json`),
self time at N = 0 / 1k / 4k / 16k, the functions that scale:

| function | 0 | 1k | 4k | 16k |
|---|---|---|---|---|
| `Engine._idx` (per-call fact index build) | 0.004 | 0.048 | 0.187 | 0.958 s |
| `_valid_fast` (whole-state validation of every mutating call) | 0.003 | 0.047 | 0.174 | 0.744 s |
| `reference.index` (per-call relation index) | 0.001 | 0.024 | 0.113 | 0.645 s |
| `relations()` (scan of every fact) | 0.002 | 0.039 | 0.146 | 0.626 s |
| workload total | 0.10 | 0.38 | 1.36 | 5.91 s |

## 2. Mechanism: `--incremental` (requires `--indexed` and static retention)

- **Persistent fact index** (`Memo.ix`): the reference build's structures (names, positions, decode,
  out-relations, triples, `reference.index`, ids) plus per-relation/subject/object/(s, r) lists, a
  told-relation counter, bit → code lists and the list of small packets. Built once (the same code
  as the per-call build, then adopted), and kept across calls while it is valid: the state's fact
  list is the same object, has the indexed length and the same fact epoch. `tell` maintains it on
  append (same insertion order as a fresh build) and on a new support; any removal (`_drop`, the
  only other writer of facts) replaces the list, so the next use rebuilds it.
- **Indexed reads:** `relations()` from the told-relation counter; `_find` from the (s, r) lists
  (fact order); `_rows` from persistent sparse per-relation rows; `tell`'s "was the subject known"
  from the index positions (equal to the reference's entity set: facts at its first use plus every
  fact told since, with no removal in between; a removal materializes the reference set first).
- **Exact recall candidate filter** (the first pass of a new (s, r) key): the reference test is
  2|q&p| > |p| with q = b(s,0) ^ b(r,1), p = b(s',0) ^ b(r',1) ^ b(o',2). q's bits lie in b_s ∪ b_r,
  so passing needs |b_s & p| ≥ |p|//2 + 1 − |b_r|; p's bits lie in its three codes, so one code X has
  |b_s & X| ≥ ⌈(|p|//2 + 1 − |b_r|)/3⌉, which is ≥ 2 whenever |p| ≥ 38 (|b_r| ≤ 16). Candidates are
  the triples of every code sharing ≥ 2 bits with b_s plus every packet with |p| < 38; each is then
  tested exactly. **Honest scope:** finding the codes visits |codes|·16/4096 code entries per new key
  — linear in the number of distinct codes with constant ≈ 1/16, not asymptotically sublinear. A
  pair index would be sublinear but was rejected for memory (≈ 1.9 M entries at 16k facts).
  With real codes the candidates were 3.2 % of the triples in the unit check.
- **Sparse prediction tables in `_scan`:** the table holds only the domain and negative-statement
  entities (in entity order); `_differs` also visits the program's own domain in entity order, so it
  makes the same visits as with the full table.
- **Change-scoped validation** (serve): a mutating call is validated by `_valid_scoped` — every
  non-fact check of `_valid_fast`, and the per-fact checks only on the facts this call appended or
  gave a new support (premises resolved through the index's ids) — when the call removed nothing,
  the index stayed valid, the open state had been fully validated, and fewer than **K = 64** mutating
  calls passed since the last full validation. Otherwise (and at every snapshot) the full
  `validate_lean` runs, plus `ix_check` (the index equals a fresh build and the told-relation counts).
  K = 64 is registered here (env `PACKETLM_FULL_VALIDATE_EVERY` only for tests).
- **Guard proof (tests):** `g57b_period_guard_catches_untouched_corruption` injects a corrupted
  untouched fact (supports removed); calls 2–4 pass scoped validation (that is the scope: corruption
  outside a call's changes is caught at the period), call 5 (the period, K = 4 in the test) raises,
  the call is not kept, and the state reloaded from snapshot + journal equals a never-corrupted
  run's state and replies. `g57b_period_guard_catches_index_corruption`: a corrupted index is caught
  by `ix_check` at the period. Corruption is never snapshotted: a snapshot is a full validation.

What still scales with total state (not removed by G57b, measured in §5): removals (`_drop` loops
and the rebuild), the full validation every 64 calls and at snapshots, snapshot writes, the
union-find build the first time components are needed after a rebuild, recall-entry updates per
append (O(cached keys)), non-fact validation parts (grow with capabilities/observations), and
programs whose domain is every entity.

## 3. Exactness

Xj must give byte-identical replies and state to Xi (the G57 engine). Checks (section `g57b`, 10, including the Info 2 check of §4d):
the G57 differential (11 targeted scenarios + 40 random sessions) against the G57 engine at K = 64
and K = 3, with every new path exercised (scoped and full validations, rebuilds, appends, candidate
queries); candidate superset of the passing set with real codes and with dense codes (128 bit
positions: small packets and multi-bit overlaps common); index/`relations()`/`_find` equal to the
reference after random tells and retractions with `ix_check`; both guard tests; scoped validation
rejects a broken touched fact or a dangling premise; the candidate bound's tight case (a 38-bit
passing packet whose codes each share only 2 bits with b_s); derived-then-told relations. The
G57b differential also compares the engines' work counters (`stats`, e.g. `grown_requalified`), and
has two more targeted scenarios (a negative statement outside the candidate's domain; an
object-only entity re-told after its facts were removed in the same call). 17 mutations (the Info 2 key; hooks, candidate threshold, small list, sparse tables,
was-known, scope flags, premises, `ix_check`, period guard).

## 4. Design (registered)

### 4a. Part S (fresh seeds)

`benchmarks/g57b_scale.py`: the G57 part S protocol (padding, workload, charging, bootstrap from
`benchmarks/g57_scale.py`), seeds **231–237**, N = 0 / 1000 / 4000 / 16000, 10 tasks, arms Xs, Xi, Xj.
Changes after verify-35bda6b (registered here, before any G57b registered run):
- **Low 1:** N = 0 lacks the padding relations, so it is not the same relevant state. Rule F's
  baseline is **N = 1000** (every padding relation present): R1k_N = mean task CPU at N ÷ at 1000.
  R against N = 0 (G57's form) is also reported.
- **Low 3:** every arm is snapshotted (uncharged) right after padding; the 50 workload calls stay
  below the 64-call interval, so no arm snapshots inside the timed window (guard
  `guard_no_snapshot_in_window`). A final snapshot (for Xj, also the full validation and
  `ix_check`) is timed separately (`snapshot_cpu_s`), and an amortized per-task cost adds
  journaled calls per task ÷ 64 × that snapshot (`R1k_amort_N`, reported, not a criterion).
- **Low 2:** the receipt records HEAD, `git status --porcelain`, source and engine hashes and the
  lock file contents at start and end; `benchmarks/g57b_registered.sh` creates the lock, runs both
  parts, deletes the lock and writes the create/delete times to `g57b_lock.json`.

Guards: Xi and Xj reply streams equal Xs at every (seed, N); Xj final state bytes equal Xi's; the
workload answers are the same at every N; no snapshot in the timed window; source unchanged.

- **Material (anti-circling rule, from the 05:33 request):** G57b is material iff Xj's R_16000
  (against N = 0, the form G57's 91.9 was measured in) has upper 95 % CI bound ≤ **45.95**. If not
  material: stop and report; no iteration. (G57's 91.9 included no in-window snapshot for Xi, per
  the verifier, so the comparison is like for like.)
- **Rule F re-tested:** flat iff Xj's **R1k_16000** upper bound ≤ 1.25.
- Predictions (from dev, §5): material holds; rule F fails (dev R1k_16000 ≈ 2.9).

### 4b. L1 / L3 contrasts (fresh seeds)

`benchmarks/g57b.py`: the G57 long-lived protocol (G50 `complete` teacher, whole-process CPU with
maintenance, instrument 70297af unmodified), comp seeds **241–247**, unrel seeds **251–257** (sealed in
`benchmarks/sealed_tokens_g57b.json`), arms Xi and Xj for C, B, P (and F, comp).

- Primary: **L1j** = A(Cj+maint ‖ Bj) (comp), **L3j** = A(Cj+maint ‖ Bj) (unrel), and
  A(Cj+maint ‖ Ci+maint) (both). Secondary: Ci+maint‖Bi, Bj‖Bi, Pj+maint‖Pi+maint, Cj+maint‖Pj+maint,
  Cj‖Bj, and for comp Fj+maint‖Fi+maint, Cj+maint‖Fj+maint.
- Claims: L1j / L3j claimed iff CI lower > 0 (amortization; not expected). "Mj" claimed iff
  A(Cj+maint ‖ Ci+maint) CI lower > 0. Guard: Xj replies and state bytes equal Xi's (every role and
  seed), 0 wrong-qualified, instrument pinned and unmodified.
- Outcomes (solved, qualified, censored, library use) are reported separately from cost; C and B are
  not accuracy-matched when their solved counts differ.
- Predictions (dev): Mj holds in unrel; L1j and L3j negative but smaller gaps than G57's.

One mutation is observably equivalent and survives by design: `g57b_drop_keeps_scope` (a removal
also marks the scope not-ok). A removal replaces the fact list, so the index is invalid until a
rebuild, and a rebuild marks the scope not-ok itself; the flag is defence in depth.

### 4c. Comp library-scan profile (for G58)

`benchmarks/g57b_profile.py --comp 961`: one comp C arm under cProfile, Xi and Xj flags; reported
as the setup for G58 routing (descriptive, not a claim).

Measured before registration (dev seed 961; `docs/evidence/g57b/profile_before.json` (Xi) and
`profile_after.json` (Xj); the Xj profile ran beside a mutation run, so absolute times are noisy):
whole C arm 17.65 s (Xi) / 18.08 s (Xj) — G57b does not touch the comp cost. Of Xj's 18.1 s,
`acquire` 15.4 s; `_scan` 12.9 s cumulative over 123 scans (3.3 s self), its inner `step` 6.3 s over
1.23 M calls; `_fc_requalify` 4.5 s (40 calls); `hypotheses` 2.4 s; `execute` 2.9 s over 110 k calls.
So the comp gap is the qualification scan over library × primitive programs, per acquisition:
G58 (adaptive capability economics) should route which capabilities/primitives a scan considers
and when requalification re-scans, not index facts.

Part S profile after G57b (Xj, seed 991, workload CPU at N = 0 / 1k / 4k / 16k): 0.072 / 0.079 /
0.109 / 0.243 s (G57 Xi: 0.10 / 0.38 / 1.36 / 5.91). What still grows: `expand`/`execute` (programs
whose domain grows with padding capabilities), the union-find build the first time components are
needed after a rebuild (`_union`/`_find`, 16 k calls at 16k, once), `region_hits`, the recall
candidate counting, and fsync/snapshot size (outside the timed window, reported separately).
