# G57: state-proportional cost under the long-lived protocol (`--indexed`)

Request at 04:40 (America/New_York, 2026-11-27): under one pre-registration,
(a) evidence-gated maintenance re-asks: skip only when nothing the answer depends on changed since
its last answer, with an exactness argument and an adversarial differential test against
always-re-ask; (b) relation/component-indexed recall and scans, so unrelated state adds no cost.
Exactness: replies and state byte-identical to the non-indexed, always-re-ask engine. Measured under
serve with all arms equal, new seeds, at least 7 per curriculum, instrument 70297af; primary
contrast L1/L3 against B.

Pre-registered before any registered seed is run. Coordination rule: the registered run is
started only with `/workspace/REGISTERED_RUN.lock` in place (start time, experiment name), with no
dev work running beside it; the lock is removed right after.

## 1. Why (G56)

Under the long-lived protocol (G56), C's gap to B was 2.13× (comp) and 18.0× (unrel). On unrelated
knowledge 77% of Cs's CPU was maintenance re-asks (504 calls, about 22 ms each, against B's 2 ms
per call). A dev profile (seed 963) put 2.1 of Cs's 4.5 s in `answer`, 1.7 s of it in recall over
every stored packet; validation 0.7 s, index builds 0.5 s, `relations()` 0.2 s,
`reference.index` 0.2 s. On comp, Cs's cost is dominated by the scan over library programs
(`_scan` 10.9 of 16.7 s), which is library-space work, not unrelated state.

## 2. Mechanism: `--indexed` (packetlm/engine.py `Memo`, packetlm/serve.py)

`--indexed` adds caches that hold no state and never decide anything themselves. Under serve one
`Memo` lives as long as the open state (it is dropped with it on close, path change or a failed
call); per process it is fresh in every call.

- **(b1) Relation-grouped rows.** `_rows(rel)` takes the triples of `rel` from a grouping built
  once per index, instead of filtering all triples for every relation. Same triples, same order.
- **(b2) Memoized recall.** `Memo.recall[(s, r)]` holds exactly the triples whose packets pass the
  reference recall test 2|q&p| − |p| > 0 for q = bind(s, r). The first ask of (s, r) tests every
  packet once (as the reference does every time); after that `Memo.sync`, run whenever the engine
  builds its fact index, applies the multiset difference between the triples the memo reflects and
  the index's triples: a removed triple leaves the entries that hold it, an added triple joins an
  entry iff its own packet passes. Decoding of residues, de-duplication and sorting are the
  reference's. Packets are cached per triple, aligned with the index (a mismatch is a StateError).
- **(b3) Component classes.** The growth re-scan (`_flush_growth`) asks, for each qualified
  capability, whether a grown subject lies in the BFS region of its domain and observed subjects.
  The memo keeps union-find classes over the non-`cap:` fact edges: unions for added edges; any
  removed edge discards the classes, which are rebuilt on next use. The region is the seeds plus
  the classes of the seeds that have edges, which is exactly what the BFS visits.
- **(a) Evidence-gated re-asks.** A call whose every line is a question (`what is S W` or
  `ask S W`, normalized as `Engine._turn` does) is *read-only*. Inside a read-only call, when
  recall is unknown and the answer goes to the capability path, the answer is taken from
  `Memo.answers[(s, word)]` if the stored fingerprint equals the current one; otherwise it is
  computed by the reference code and stored. The fingerprint is:
  1. the target (after the lexicon);
  2. the full records of the target and of every capability reachable from any of its versions
     through `cap:` steps, including those inside programs (status, seq, pinned versions, domain,
     express, evidence, history);
  3. the base relations of the current executable version's expansion, and each one's change stamp
     (`Memo.stamp[r]` is bumped whenever a triple with relation r is added or removed);
  4. whether s is a known entity;
  5. the construction library.
  The gate is active only with geometric execution, no programs, no operators and static
  retention (the configuration whose reads 1–5 cover; every G57 arm has it). Record hashes are
  computed once per read-only call, which is sound because nothing changes inside one.
- **Read-only calls under serve** are neither re-validated nor journaled: the state is the one
  validated and journaled when it last changed. With `PACKETLM_CHECK_READONLY=1` (always on in the
  tests) the server hashes the state before and after every read-only call and fails if it moved.

**Exactness argument.**
- (b1), (b2), (b3) compute the same sets the reference computes, from the same triples: (b1) is a
  grouping; (b2) maintains the passing set under exact multiset differences, and the test of a
  triple depends only on that triple's packet and q; (b3) maintains connectivity exactly for
  additions and recomputes it after removals. Decoding, order normalization and every decision
  after them are unchanged.
- (a): within the gate, `answer` reads recall (decided exactly by (b2), and the gate is consulted
  only when it is unknown) and then `_answer_exec`, which reads: the target's current version
  (status, seq, domain), its execution, i.e. `expand(seq)` (the records of the `cap:`
  dependencies) and the rows of the expanded base relations (only triples with those relations,
  and the position of s); `say` reads the library and the target's `express`. Each of these is in
  the fingerprint or is a function of it. If the fingerprint is equal, every input of the
  computation is equal, so its output is equal. The question branches of `_turn` do not write the
  state, which the read-only check verifies on every read-only call in the tests.
- Components 4 (known entity) and the dependency closure in 2 are conservative: with the current
  engine, a dependency's change also changes the dependent's own record (status propagation) and
  a newly known entity only changes stamps. They are kept and tested at the fingerprint level.

## 3. Design (registered)

- Harness `benchmarks/g57.py`: G56's serve protocol and teacher (G50 `complete` teacher, whole-process
  CPU with maintenance, instrument 70297af); flags `--answers --bounded --lean`, B and P add
  `--no-library`.
- Arms, every one under `python -m packetlm.serve`: **Xs** (reference: non-indexed, every re-ask
  executed) and **Xi** (same flags + `--indexed`), for X in C, B, P, F (F comp only). B opens a new
  empty state path for every task in both.
- Seeds: comp (G46 worlds) **201–207**, unrel (G46-U worlds) **211–217**; sealed in
  `benchmarks/sealed_tokens_g57.json` before the run.
- Every finished arm run is written to disk at once (`<seed dir>/job.json`, `progress.jsonl`).
- Contrasts (cost ratio = 1 − A; S = 7; decision "claimed" iff the 95% CI lies above 0):
  - **L1i (comp) / L3i (unrel): A(Ci+maint ‖ Bi)** — all arms equal. Co-primary, the 04:40 wording:
    **A(Ci+maint ‖ Bs)**.
  - **Mi: A(Ci+maint ‖ Cs+maint)** — what `--indexed` saves the library learner.
  - Secondary, descriptive: A(Bi ‖ Bs), A(Pi+maint ‖ Ps+maint), A(Ci+maint ‖ Pi+maint),
    A(Cs+maint ‖ Bs) (G56's L1s/L3s on new seeds), A(Ci ‖ Bi), F lines on comp; CPU per arm,
    maintenance CPU, per-call costs.
- **Guards** (any failure makes the run invalid; it is recorded, not re-run on these seeds):
  - Ei: for every role and seed, the Xi reply stream equals Xs's (sha256, call by call) and the Xi
    final state file is byte-identical to Xs's;
  - 0 wrong-qualified sealed answers in Cs and Ci;
  - instrument pinned and unmodified; all reports ran; source unchanged during the run.

### 3b. Part S: cost against accumulated unrelated state (audit (c) of d6cbcf3)

- Harness `benchmarks/g57_scale.py` (in-process server; docstring has the full design). A fixed
  workload (T = 10 tasks: a fresh relation with a 6-fact chain, 3 examples, 3 read-only re-ask
  calls of 6 questions over this and earlier tasks' capabilities) runs after padding the state
  with N unrelated facts over 20 padding relations plus N/500 padding capabilities, for
  **N ∈ {0, 1000, 4000, 16000}**, seeds **221–227**, arms Xs and Xi. The workload never touches
  padding, so relevant state is the same at every N. Charged: process CPU of the workload calls,
  per task; the padding load is uncharged and reported (`pad_cpu_s`, which for Xi includes building
  the memo: index build and maintenance cost, audit (d)).
- Guards: Xi replies equal Xs replies at every (seed, N); the workload's known answers are the same
  at every N.
- **Rule F (flat):** R_X = mean task CPU at N = 16000 ÷ at N = 0, per seed; mean over seeds with a
  95% bootstrap CI (5000 resamples). **Claimed for Xi iff the CI's upper end ≤ 1.25.** R is also
  reported for Xs, at every N.
- Each (seed, N, arm) result is written to disk as it finishes.
- **Corrections (verify-35bda6b, after the run; the registered text above is kept):** Low 1 — "the
  relevant state is the same at every N" overstates N = 0: at N = 0 the padding relations are absent,
  so the workload's scans see fewer relations; only N ≥ 1000 share every padding relation. G57b's
  part S uses N = 1000 as the rule F baseline and also reports N = 0. Low 3 — read-only indexed
  calls are not journaled and so do not count toward the 64-call snapshot interval: in the timed
  window only Xs at N = 16000 paid one snapshot (small; slightly inflates Xs's R_16000 and the Xs−Xi
  gap; Xi's rule F decision is unaffected). G57b's part S snapshots every arm before the timed window
  and charges none inside it, and reports the snapshot cost separately. Info 3 — the comp Mi effect
  (+0.041) is small and timing-sensitive (the verifier's 2-seed rerun interval touched 0).

### 3c. Reporting (audit (b), (d) of d6cbcf3)

- Reported separately per arm and curriculum: cost-to-target (whole-run CPU and per task), tasks
  solved, qualification status, library use, and censoring (tasks whose run hit a limit or ended
  without a decision; a harness exception ends the run, which is then recorded as failed).
- **The contrasts are not perfectly accuracy-matched.** In G56 comp, C solved 252 tasks against
  B's 247 (P 247); A(C‖B) compares runs that did slightly different amounts of work. This is
  stated beside every L1 line.
- All index build and maintenance cost is inside the charged CPU: the memo is built and maintained
  in the same server process, during charged calls.
- Primary hypothesis framing (audit): *a continual learner can retain an expanding body of
  knowledge without every computation inspecting or re-verifying all of it.* G57 is a test of it,
  not an assumption: rule F is the direct test.

**Reading.**
- All predictions held: Ei held; Mi claimed on both curricula (unrel +0.59; comp small, +0.04);
  L1i, L3i and rule F not claimed.
- Exact gating and indexed recall remove most of the **maintenance** cost on unrelated knowledge
  (12.46 → 2.72 s, −78%) and cut the unrel utility penalty from 17.1× (Cs vs Bs) to 6.9× (Ci vs
  Bi), with byte-identical replies and states.
- They do not make cost proportional to relevant state. The primary hypothesis (*a continual
  learner can retain an expanding body of knowledge without every computation inspecting or
  re-verifying all of it*) is **not supported** by this engine yet: every call still rebuilds the
  fact index, re-validates the whole state after every mutating call, recomputes `relations()`,
  and passes over every packet on a new recall key. Even with no maintenance, Ci costs 4.1× Bi on
  unrel (A = −3.07).
- On comp the library scan dominates; G57 does not address it (Mi +0.04).
