## 1. `--incremental` exactness and the change-scoped validation

**Tool:** `tools_8994490/incr_diff.py`. I wrote it independently of `g57_diff.py` and the g57b checks.

Four in-process `serve.Server`s run each session:
- **REF:** no `--indexed`, so every re-ask is executed.
- **XI:** `--indexed`.
- **XJ:** `--indexed --incremental`, read-only check on, K given by the run.
- **XJ64:** the registered configuration, K = 64.

After **every call** it compares the replies and `json.dumps(state)` byte for byte. It also compares the XI/XJ/XJ64 work counters (`stats`). With `--deep`, it rebuilds **every** persistent-index structure from scratch and compares: names, pos, out, triples, ref, byid identity, by_rel, by_s, by_o, by_sr (identity), told_rel, codes, codebits, small and decode. At the end it compares snapshot bytes REF = XI = XJ = XJ64, and journal bytes XI = XJ = XJ64.

**Operations covered:**
- fact add, re-tell (support append) and derive followed by `fact x cap:N y`;
- retract (3-arg, 2-arg, absent), correct and complete;
- an object-only entity losing all its facts, then re-told as object or subject, also inside one call;
- mixed append + removal + append calls, and brand-new subjects (alone or after a removal);
- `!none`/`!several`, contradicting and corrected examples;
- investigate, requalify, revoke and learn;
- `cap:` dependencies and re-teaching (replacement or demotion);
- define, express, construct, question, new relations, observe, unanswered, why, show and capabilities;
- memo drops, crashes between calls (Server abandoned and journal replayed) and torn journal tails;
- padding of 0, 1k or 16k facts (the `g57_scale.padding`), and append-only streams, so that the K = 64 period fires on its own.

### 1b. Attacking the K = 64 guard: injected corruption (`corrupt_probe.py`)

For each session I injected a corruption into the in-memory state, or into XJ's persistent index, at a random call. That session then ran beside a never-corrupted twin. State corruptions were also run on XI (the G57 engine, fully validated every call). I did 60 sessions per kind at K = 4 and at K = 64 (`logs/adv/corrupt_K*.log`).

**State corruptions of an untouched fact:** empty supports, dangling premise, id mismatch, a `bits` key, a duplicate append, a bad capability `current`.
- XI catches each at the next mutating call.
- XJ catches each at the period (latency ≤ K mutating calls, observed max 13 at K = 64, because removals force full validations earlier), at the next removal, or at close/snapshot.
- Read-only calls do not count toward K, so any number of them are served from the corrupt state in between (181 at K = 64).
- Non-fact corruption (`current`) is caught immediately by the scoped validator.
- When the corruption did not affect replies, the reopen (snapshot + journal) and a retry of the refused call gave exactly the clean state.
- When it did affect a reply: 1/60 (empty supports, K = 64), and 2/60 plus 3/60 (empty supports and an in-place change, K = 4). The journaled records no longer replay, so the reopen fails with `journal replay diverged at record k`. The path is then unopenable until it is reset by hand (Low 2).

**In-place valid change** (a fact's `o` and `id` rewritten consistently): XI never detects it, because the state is valid. XJ detects it only when the index survives to an `ix_check`. In 53/60 runs a removal rebuilt the index first and erased the evidence.

**Index corruptions:**

| corruption | detected (K=64) | wrong replies served | wrong final state persisted, undetected |
|---|---|---|---|
| told_rel off by one (covered by ix_check) | 7/60 (at close), 53/60 healed by a rebuild | 0 | 0 |
| `ref` entry dropped (covered) | 7/60 at close, 53/60 healed by a rebuild | 2/60 | **10/60** |
| `by_sr` entry dropped (not covered) | 0/60 | 3/60 | 3/60 |
| `by_rel` entry dropped (not covered) | 0/60 | 11/60 | 7/60 |
| candidate (`small` + `codebits`) dropped (not covered) | 0/60 | 10/60 | 0/60 |

**So, to the question asked:** yes, corrupt or inconsistent state can persist undetected between full validations. That is the documented scope for untouched facts, but it also holds across unbounded read-only calls. Injected state corruption is caught at the next full validation. Index divergence is caught only in the core structures, and only if no removal rebuilds the index first. Divergence in the secondary structures is never caught (Low 1). No such divergence occurred organically: the deep check covered all of these structures with 0 differences over 420k comparisons.

## 2. `g57b_drop_keeps_scope` is equivalent

**Argument:**
- `_drop` always assigns a new fact list. The persistent index holds the old list, so `ix_valid` is false until a rebuild.
- `_validate` requires `ix_valid` for the scoped path.
- The only rebuild (`_idx` → `ix_adopt`) sets `scope["ok"] = False` itself.
- So whenever the mutant's flag differs, a full validation runs anyway.

**Trace check** (`mutant_equiv.py`): the original and the mutant ran in separate processes (PYTHONHASHSEED 0 and 7), with a per-call trace of the validation path, the ok flag, the touched count, `ix_valid`, `ix_checks`, the replies hash and the state hash. I used 150 long sessions (5% crashes) at K/snap = 3/8, 64/64 and 64/200. That is 21,769 calls and 10,292 validations each.
- The ok flag differs at 487 validations, and in all 487 `ix_valid` was false.
- The validation path, replies, state and `ix_checks` were identical in every call (`logs/mutequiv/compare.json`).

I could not construct a distinguishing input.

## Findings by severity

**High:** none. **Medium:** none.

**Low**

1. **`ix_check` covers only the core index, and any removal discards the index unchecked.**
   - The K-period and snapshot guard compares names, pos, out, triples, ref, byid and told_rel. It does not compare by_rel, by_s, by_o, by_sr, small, codes, codebits, decode or prow, which serve `_rows`, `_find` and recall.
   - A removal rebuilds the index without first checking the old one.
   - With injected divergence, wrong replies were served and wrong state was persisted with no detection: by_rel 7/60, by_sr 3/60, and even ref 10/60, healed by a rebuild before the check.
   - G57b.md's "the index equals a fresh build" and "a corrupted index is caught by ix_check at the period" are true only for the core structures, and only when no removal intervenes.
   - No organic divergence was found: 420k deep checks, 0 differences.
   - Suggest checking every structure in `ix_check` (O(F), at the same points), and running it before a removal discards a valid index (at least periodically).

2. **Detection is deferred past calls that are kept.**
   - Between full validations, corrupt state is served on up to K−1 mutating calls and on any number of read-only calls (read-only calls do not count toward K), and those calls are journaled.
   - If the corruption changed a reply, the reopen fails with `journal replay diverged`. The path then needs a manual reset, losing the calls since the snapshot (observed 1/60 at K = 64).
   - G57 refused the culprit call itself.
   - This fails closed, with no silent persistence for detectable corruption. But the guard-test claim, that the reload equals a never-corrupted run, holds only when the corruption did not affect replies. Suggest stating that.

3. **The K = 64 period never fires on its own under the registered defaults, and its cost is left out of R1k_amort.**
   - `since_full ≤ since` and both reset at a snapshot. With SNAPSHOT_EVERY = FULL_VALIDATE_EVERY = 64, the period call is always a snapshot call.
   - So every 64 calls Xj pays `validate_lean` + `ix_check` twice: once in `_validate` and again in `_snapshot`/save. This was seen in append62: ix_checks ≈ 2 × the period count.
   - In adversarial sessions removals force full validations so often that the period fired only in append-only streams.
   - The extra cost at 16k is 34.5 ms per 64 calls. Including it, R1k_amort_16000 rises from 3.96 [3.45, 4.39] to **4.23 [3.71, 4.67]** (`period_cost.py`). This is reported-only; no criterion changes.
   - Suggest skipping the `_validate` full pass when a snapshot follows in the same call, or charging it.

**Info**

1. `g57b_drop_keeps_scope` is equivalent (§2).
2. The `ix_support` told_rel increment is unreachable from the command language. Non-cap facts always keep a told support, and derived facts exist only on `cap:`. `g57b_support_skips_told_rel` is therefore effectively equivalent for states built through the command language. It is reachable only from a hand-made state file, and only the builder's direct test kills it.
3. The N = 1000 stop rule was added (cf511ba) after the dev result R1k 2.89 on dev seeds. It is a conjunctive tightening, so it cannot make "material" easier. G57b.md says "finalized 07:50 EST", but that text sits in a commit made at 07:38:51; this is cosmetic.
4. Comp Bj‖Bi is a small, timing-sensitive effect. On seeds 241 and 245 the registered value is +0.015 and my re-run gives −0.031. "The index costs fresh small states a little" should be read as noisy in comp; unrel's −0.12 to −0.17 is consistent.
